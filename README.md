# PoC Task Planner

일정 관리 앱에 필요한 화면과 사용자 흐름을 빠르게 만들고 검토하기 위한 기획용 프로토타이핑 저장소입니다.

이 저장소의 목표는 완성된 제품을 만드는 것이 아닙니다. 떠오른 아이디어를 실제로 조작할 수 있는 화면으로 빠르게 옮기고, 팀이 함께 사용성과 필요성을 확인한 뒤 가치 있는 화면만 남기는 데 집중합니다.

## 작업 원칙

- 속도를 완성도보다 우선합니다.
- 디자인 시스템이나 픽셀 단위의 완성도에 과도하게 투자하지 않습니다.
- 백엔드 없이 목 데이터와 브라우저 상태만으로 화면 흐름을 표현합니다.
- 재사용 가능성이 분명하지 않은 코드를 미리 추상화하지 않습니다.
- 한 브랜치에서는 하나의 화면 또는 하나의 사용자 흐름만 다룹니다.
- 화면의 필요성을 검토한 뒤에만 `main` 브랜치에 병합합니다.

## 기본 기술 스택

- Vite
- React
- TypeScript
- React Router (화면별 경로가 필요할 때)
- CSS Modules 또는 단순 CSS
- 목 데이터와 `localStorage`
- npm

새 라이브러리는 화면을 더 빨리 검증하는 데 꼭 필요한 경우에만 추가합니다. 실제 API, 데이터베이스, 인증, 배포 인프라는 프로토타입에서 요구되지 않는 한 만들지 않습니다.

## 현재 베이스라인

`main`에는 이후 화면 실험의 출발점으로 사용할 기본 Todo + 일정 관리 화면이 들어 있습니다.

- `/calendar`: 월간 달력과 선택한 날짜의 일정 관리
- `/todos`: 선택한 날짜의 할 일과 완료율 관리
- 상단 내비게이션을 통한 두 페이지 이동
- 이전 달과 다음 달 이동, 오늘 날짜로 복귀
- 날짜별 일정 조회와 새 일정 추가
- 날짜별 할 일 추가, 완료 처리, 삭제
- 할 일 완료율 표시
- `localStorage`를 이용한 브라우저 내 데이터 유지
- 데스크톱과 모바일 반응형 화면

## 로컬 실행

```bash
npm install
npm run dev
```

배포용 빌드를 확인하려면 다음 명령을 사용합니다.

```bash
npm run build
```

## 작업 흐름

1. 만들 화면이나 검증할 사용자 흐름을 작게 정의합니다.
2. 최신 `main`을 기준으로 작업 브랜치를 만듭니다.
3. Codex 같은 코딩 에이전트와 함께 화면을 빠르게 구현합니다.
4. 로컬에서 화면과 주요 상호작용을 확인합니다.
5. 변경사항을 커밋하고 원격 브랜치에 푸시합니다.
6. PR에 화면의 목적, 확인할 내용, 스크린샷을 남깁니다.
7. 팀이 실제로 필요한 화면인지 검토한 뒤 병합하거나 폐기합니다.

브랜치 이름은 다음 형식을 권장합니다.

```text
screen/<화면-이름>
flow/<사용자-흐름>
experiment/<검증할-아이디어>
```

예시:

```text
screen/calendar-week-view
flow/create-and-reschedule-task
experiment/quick-add-task
```

## PR 체크리스트

- 화면 또는 흐름의 목적이 한 문장으로 설명되어 있는가?
- 검토자가 직접 실행하고 조작할 수 있는가?
- 목 데이터만으로 주요 상태를 확인할 수 있는가?
- 이번 검토와 무관한 변경이 섞이지 않았는가?
- 주요 화면의 스크린샷 또는 짧은 영상을 첨부했는가?

코딩 에이전트를 사용할 때의 상세 작업 규칙은 [AGENTS.md](./AGENTS.md)를 따릅니다.
